# GemmaCare V1 security audit — October 22, 2026

## Scope and evidence

The audit started from a fresh, isolated clone of GitHub `main` at `e068cdf1912130d133a163486b1d6d8058b223e9`. No other local GemmaCare project supplied audit evidence or source changes. Production services, credentials, databases and model endpoints were not accessed or changed. Tests use mocked identities, generated audio, and a disposable synthetic SQLite database.

All first-party Node/TypeScript server modules, API registrations, authentication/cookies, database adapters/schemas/migrations, input/media handling, frontend rendering/storage paths, shell launchers and Docker configuration were inspected. The complete root package manifest and pnpm lockfile were inspected, including production, development and optional dependency paths. Git history was checked for obvious provider-token/private-key patterns across 160 unique blobs; this is a bounded scan, not proof that no secret exists. Public example signing keys and database passwords are security-relevant defaults, not verified active production credentials.

There is **no PHP source, PHP runtime configuration, Composer manifest or Composer lockfile** in this GitHub tree. There is one `package.json` and one `pnpm-lock.yaml` (format 9); no npm lock/shrinkwrap, Yarn lock or Bun lock exists. There are no submodules or LFS pointers. No present manifest or lockfile was inaccessible. Installed global software and other local GemmaCare projects are outside the audit.

The dependency assessment independently retrieved all **161 distinct official GHSA records** corresponding to **176 baseline package/range records**, and compared exact locked versions with upstream affected ranges. These are scanner matches, not a count of confirmed application exploits. See [every advisory, version and reachability assessment](SECURITY_ADVISORIES.md).

Non-loopback production listeners require a 16+ character application password, checked before JSON parsing and for static/API/login paths. ## PHP and Node runtime review

The [PHP security announcement dated October 21](https://www.php.net/index.php) describes CVE-2026-109618 and CVE-2026-109619 in PHP web runtimes. Neither PHP nor Composer components are present, so these do not establish a GemmaCare vulnerability. An independently deployed PHP reverse proxy or separate service cannot be assessed from this repository.

The original repository specified a floating `node:22-alpine` image and documentation accepting Node 22 or higher; there was no exact deployed patch version to verify. The audited baseline is now **Node 22.23.4**, recorded in `.nvmrc` and both Docker stages. It is the [official October 21 security release](https://nodejs.org/en/blog/release/v22.23.4), and its Docker tag was verified against [official image metadata](https://hub.docker.com/_/node). The macOS ARM64 test runtime was downloaded from nodejs.org and checked against the vendor SHA-256 manifest. No system-wide runtime was replaced.

The [October Node security notice](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases) includes DNS/TLS, Brotli, keep-alive, entropy-cache and permission-model fixes. For this app, DNS/TLS destinations are server configuration; Brotli exposure would require attacker-controlled compressed input on a used decoder path; no user startup snapshots, permission-model flags or ZipFile API are configured. These facts do not establish exploitation on an unknown deployed runtime. The pinned runtime includes the release's fixes; deployed installations still need their own version verification/update. Other Node majors and operating systems were not compatibility-tested.

Node 22 remains an [LTS release line](https://nodejs.org/en/about/previous-releases). Node 18/20 and odd-numbered EOL releases should not be treated as supported deployment targets. The old SQLite binding remains 9.6.0 (native SQLite 3.45.3, independently queried in the built image) to preserve compatibility; the patched Node build needs native compiler prerequisites where prebuilt bindings are unavailable. Docker provides those tools for compilation and removes them from the runtime install layer afterward.

The native SQLite library is separate from Node’s built-in SQLite update. [SQLite’s upstream vulnerability guidance](https://sqlite.org/cves.html) identifies untrusted SQL or a hostile database file as key prerequisites. This app exposes neither a SQL console nor a database-file upload; its SQL is parameterized and schemas are static. Native-engine flaws are not asserted reachable through clinical string values, and this is not a complete native-library audit. The locally built image reports FFmpeg 8.1.2; existing host FFmpeg and Ollama versions remain unknown. The [official FFmpeg security page](https://ffmpeg.org/security.html) lists 8.1.2 as fixing CVE-2026-8461 and CVE-2026-30999. Those fixes are included in this newly built image; the floating host decoder used by existing installations cannot be classified without its exact version. Ollama is external to the repository and has no locked runtime version, so its installed vulnerability status is unverified.

## Input, injection and data boundaries

- tRPC clinical procedures use authenticated context and Zod object/type validation. SQL values use Drizzle parameters or SQLite placeholders; schema/table/alias identifiers are static. [Drizzle's identifier-injection advisory](https://github.com/drizzle-team/drizzle-orm/security/advisories/GHSA-gpj5-g38j-94v9) is a version match without an exposed identifier-construction path here. No independent IDOR was found in record/translation endpoints.
- No S3/storage-proxy upload endpoint is active. Audio and images arrive as base64 JSON, not attacker-selected filesystem names. Native fetch goes to a configured Ollama URL, not an input URL. The old shell invocation used generated paths, so request-driven shell injection was not confirmed; it now uses an argument array. Synthetic HLS probes on the available decoder did not demonstrate SSRF/file-read exploitation; the new allowlists are an additional restriction, not a claim to have reproduced that exploit.
- Clinical strings render through escaped React text in current routes. The unsafe-style helper takes code-defined chart configuration, not clinical input. Streamdown/Mermaid/DOMPurify exist in the unused AIChatBox subtree, which no route imports. Their advisory version matches remain documented; enabling that component requires reassessment.
- No Firestore/Supabase rules or other database access-rule system is present. SQLite/MySQL isolation relies on server-side ownership checks and OS/database access controls. There is no application encryption at rest or per-clinician login model.
- Prompt injection can influence model-generated clinical content; this work does not claim to solve model reliability or clinical safety. Clinical prompts, scoring rules, medication checks and crisis-resource content were preserved. Comparing the clinical helper AST against the base commit, excluding logging, produced an exact match.

## Remaining limitations

No real patient data, production credential or live model was used. The nine live-model tests are skipped; clinical accuracy and translation behavior have not been validated by this security audit. MySQL runtime behavior, Windows deployment, real TLS/reverse-proxy setup, production firewalls and deployed runtime/image digests were not inspected. FFmpeg, Ollama, MySQL image/OS package versions in existing deployments cannot be verified from this source tree. A library advisory scan is not a full manual audit of every line of vendor code or a complete native-library/OS vulnerability scan.

Plaintext SQLite/MySQL records and browser localStorage (patient details and medication tracking) remain. They are not deleted, encrypted, re-keyed or migrated. A shared OS/browser profile or application password shares the owner account. Clinical inference still has a large 150 MB request limit and no per-user rate/concurrency quotas; trusted callers can exhaust model/decoder resources. Database/model backups and filesystem access need operational protection. Historical Git artifacts and logs remain outside this patch's cleanup scope. See README upgrade instructions before applying the source changes to an existing data directory.

No merge, release, deployment, production credential change or production-data operation is part of this audit.
